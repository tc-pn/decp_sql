# DECP Data Engineering Project

## Overview

This project is a Data Engineering pipeline built around the French **Données Essentielles de la Commande Publique (DECP)** dataset.

The goal is to build a reproducible pipeline that:

- acquires the official DECP data;
- preserves the source data;
- cleans and validates it;
- handles data-quality and record-identity issues explicitly;
- builds an analytical PostgreSQL database;
- eventually supports repeatable and incremental ingestion.

The project is deliberately developed in stages. At the current stage, the focus is on the infrastructure and RAW layer rather than on the final analytical model.

## Architecture

The target architecture is:

```text
Official DECP dataset
        │
        ▼
   Acquisition
        │
        ▼
┌─────────────────┐
│       RAW       │
│ source-oriented │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│     STAGING     │
│ typed/cleaned   │
│ validated       │
└───────┬─────────┘
        │
        ├──────────────► QUARANTINE
        │                invalid records
        │
        ▼
┌─────────────────┐
│    ANALYTICS    │
│ business model  │
└─────────────────┘
```

The important distinction is:

- **RAW** preserves the source representation.
- **STAGING** interprets and validates the data technically.
- **QUARANTINE** contains records that cannot safely proceed.
- **ANALYTICS** contains the business-oriented model used for analysis.

## Important data-model finding

A central discovery during profiling was that the DECP `id` column cannot safely be used as the primary key of our database.

We observed:

- many repeated `id` values;
- repeated `(acheteur.id, id)` pairs;
- repeated records with different amounts;
- repeated records with different holders;
- source-dependent differences.

Therefore, we do **not** assume that:

```text
id
```

or:

```text
acheteur.id + id
```

uniquely identifies one analytical contract record in the national aggregate.

This is an important reason for introducing a RAW layer before constructing the final analytical model.

# RAW layer

## Grain

The grain of `raw.decp_record` is:

> **One row in the source CSV = one RAW observation.**

Each observation receives a technical identifier:

```text
record_id
```

This identifier is generated by PostgreSQL and does **not** represent the business identity of a public contract.

The DECP source identifiers remain ordinary columns.

---

## Exact table design

The current table is:

```text
raw.decp_record
```

It contains two groups of metadata followed by the source fields.

### Ingestion metadata

```text
record_id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
source_file    TEXT NOT NULL
ingested_at    TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

`record_id` is a technical database identity.

`source_file` identifies the file from which the observation was ingested.

`ingested_at` records when the observation was inserted into RAW.

At this stage, there is **no `row_hash` column**. Hash-based idempotence can be considered later as part of the ingestion strategy.

### DECP source fields

All source fields are currently stored as `TEXT`.

The PostgreSQL column names use `snake_case`, while the source values themselves are preserved.

The DECP CSV uses `CDL` extensively as a sentinel value for absent, non-provided or non-applicable data.

Therefore:

```text
RAW       → preserve "CDL"
STAGING   → interpret "CDL" according to field semantics
```

We do **not** convert `CDL` to SQL `NULL` during RAW ingestion.

This preserves the original source representation.

---

## Source identity and future updates

The RAW table is designed to allow multiple ingestions of the DECP dataset without requiring the previous observations to be overwritten.

For example:

```text
source_file = decp-2022-marches-valides_2026-10-08.csv
ingested_at = 2026-10-08 ...
```

can coexist with a later ingestion.

However, `source_file` and `ingested_at` are currently **metadata for traceability**, not a complete incremental-ingestion strategy.

The later ingestion design will need to decide:

- how to identify an already-ingested source file;
- whether a file is a new snapshot or a replacement;
- how to make ingestion idempotent;
- whether content hashes are useful;
- how source records should be reconciled across snapshots.

## Project principles

### Preserve source data

Never modify the source representation in RAW.

### Separate technical and business transformations

Parsing and validation belong to STAGING.

Business-oriented modeling belongs to ANALYTICS.

### Do not invent business identities

If the source does not provide a reliable unique contract identifier for our analytical purpose, we do not create one using an arbitrary composite key.

### Make ingestion traceable

RAW records retain the source file and ingestion timestamp.

### Avoid premature optimization

The first implementation should be simple and correct.

Performance optimizations can be introduced after the pipeline works and its bottlenecks are understood.

   ├── typing
   ├── validation

6. Record reconciliation
   └── investigate source identity / duplicates

7. ANALYTICS
   ├── contracts
   ├── holders
   ├── modifications
   ├── subcontracting
   └── analytical views/tables

   ├── idempotence

   └── metrics

Technologies such as Airflow, PySpark or cloud data warehouses may be introduced later if they add meaningful value to the project. They are not prerequisites for the initial working pipeline.
